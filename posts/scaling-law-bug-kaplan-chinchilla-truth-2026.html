缩放定律的 Bug 与真相：当前大模型训练方式到底对不对？

AI 行业观察 2026-07-06 · 17 分钟

2026 年 7 月 4 日，一篇署名 Diogo 的博客《Scaling Laws, Honestly》在技术圈刷屏。作者是前 OpenAI 研究员 Diogo Almeida，他抛出的结论足够扎眼：OpenAI 最初那套被无数人奉为圭臬的缩放定律（Scaling Law），其实是错的，根源是一个 Bug。

这不是标题党。GPT-3（1750 亿参数，仅训练约 3000 亿 tokens）、Gopher（2800 亿参数，3000 亿 tokens）这些当年的旗舰，回头看都是「又大又欠训练」的典型。行业花在这些超大模型上的算力，按加密与科技媒体的说法，是「数百万计算小时级别」的浪费。而错误的起点，只是训练脚本里几个看似合理、实则致命的配置选择。

一个 Bug，改写了 LLM 时代最初几年的技术路线。它是怎么发生的？影响有多大？更重要的是——吸取了教训之后，我们今天的训练方式就正确了吗？模型参数规模和数据量，到底该怎么匹配？ 这篇文章一次讲清楚。

先补个课：什么是缩放定律

缩放定律的观察极其简洁：随着模型规模 N（参数量）、数据规模 D（token 数）、训练算力 C（FLOPs）的增长，训练损失 L 会沿着一条幂律曲线可预测地下降——在 log-log 坐标下就是一条直线。

一个常用近似是 C ≈ 6ND：每个 token 的前向计算约 2N FLOPs，反向传播是前向的两倍，合计约 6N。

它为什么值钱？因为可预测。你可以用一堆小规模训练跑出拟合曲线，然后外推去估计「训练一个更大的模型，需要多少数据、多少算力、大概能到什么损失」。整个「scaling-pilled（缩放信仰）」的时代，就是建立在这条曲线上的：只要往上堆算力，损失就会乖乖下降。

问题在于——这条曲线的斜率和最优配比，一旦拟合错了，会把整个行业往错误的方向带。而这正是 Kaplan 那篇论文出的事。

两代缩放定律：Kaplan vs Chinchilla

故事的两个主角：

  • Kaplan et al. (2020)，OpenAI 出品，把缩放定律带火。他们在 768M–1.5B 非嵌入参数、22M–23B tokens 的范围做实验，得出一个影响深远的结论：给定算力预算，应该把模型做得非常大，然后在收敛之前就停下。用公式说，最优模型规模 N_opt ∝ C^0.73——模型规模要比数据涨得更快。算力翻 10 倍，他们建议模型放大约 5.5 倍，而训练 token 只增加约 1.8 倍。

  • Chinchilla / Hoffmann et al. (2022)，DeepMind 出品，用更严谨的实验设计（扫了 400 多个模型，70M–16B 参数，5B–500B tokens）得出完全不同的答案：N_opt ∝ C^0.5——模型规模和数据量应该同步增长。算力翻倍，参数和数据都翻倍，经验值约为 20 tokens / 参数。

两者的分歧不是小数点后的差别，而是方向性的对立。Chinchilla 用一个著名的实验证明了自己：在与 Gopher（280B 参数）相同的算力预算下，他们训练了 Chinchilla（70B 参数，1.4T tokens）——体量小了 4 倍，数据多了约 4 倍，结果全面反超 Gopher。MMLU 上 Chinchilla 拿到 67.5% 的平均准确率，比 Gopher 高出 7 个百分点以上。

结论很清楚：当时的一大批主流大模型，都被 Kaplan 的建议带偏了，训练得太大、喂得太少。

Bug 到底是什么：三个「配料」

那么，Kaplan 为什么会算错？Almeida 的复盘给出了三个环环相扣的「配料」，缺一个都不会翻车得这么隐蔽。

配料一：所有模型用同一个固定的 token 数

这是根子上的问题。Kaplan 的实验里，无论模型多大，都训练在同一个固定的 token 预算上（约 130B tokens）。

想想这意味着什么：一个小模型在 130B tokens 上，相对它的容量是被「喂得很饱」的；而一个巨大的模型在同样的 130B tokens 上，相对它的容量是严重「饥饿」的。你拿一组「小模型吃饱、大模型饿着」的数据点去拟合，自然会得出「大模型性价比更高、应该把模型做大」的错觉。

Chinchilla 论文一针见血地指出了这个根因：Kaplan「对所有模型使用了固定的训练 token 数和学习率调度」。

配料二：cosine 学习率衰减到 0

如果只有配料一，结果会「错得很明显」，容易被抓包。真正让 Bug 藏得深的是第二个：学习率采用 cosine 调度，在到达目标 token 数时衰减到 0。

后果是：当训练接近那个固定的 token 上限时，学习率趋近于零，学习几乎停止，性能自然「平台化」。曲线看起来就像训练已经饱和、再加数据也没用了。

但我们现在知道，那些大模型如果换一个不衰减到零的学习率调度、再多喂点数据，是会继续变好的。学习率调度人为地把结果「掐断」在了 130B tokens 处，制造了一个假性饱和的假象。

配料三：宣称「结果与学习率调度基本无关」

最后一层伪装：Kaplan 论文里有一句结论，大意是训练结果「基本上与学习率调度无关」。

在「固定 token 数」这个前提下，这句话是对的。但缩放定律真正想建模的，是「数据近乎无限」的理想极限——在那个语境下，这句话就不成立了。恰恰是这句「无关」，让后来者不去怀疑学习率调度这个变量，Bug 因此更难被 debug。

Almeida 本人也在文中自嘲：他当年也在 OpenAI 做 LLM 优化，同样没发现这个 Bug——因为学习率调度看起来「明显是个重要超参数，应该是有意设定的」，谁会去怀疑呢。

三者叠加的结果

固定数据 + 衰减到零的学习率 + 「无关」的背书，三者叠加，制造出一套既错误、又极难 debug 的缩放定律。而它的直接产物，就是那句「把模型做大、别练到收敛」的建议，以及随之而来的一批 oversized、undertrained 的模型。

学术界的两种「解释」之争

值得一提的是，关于「Kaplan 为什么和 Chinchilla 不一致」，学术界其实有过两轮解释，而 Almeida 的博客明确站队了其中更硬核的一方。

主流解释（Pearce & Song, 2024）：分歧主要来自两点——Kaplan 只统计了非嵌入参数（在小模型里，嵌入层参数占比不可忽略，数不数差别很大），加上他们的实验主要在小尺度进行，log-log 外推时一点点拟合误差会被放大。这个解释很流行，也写进了很多科普。

更硬核的解释（Porian, Wortsman, Jitsev, Schmidt, Carmon, 2024，即《Resolving Discrepancies in Compute-Optimal Scaling of Language Models》）：他们在 OpenWebText2 和 RefinedWeb 两个数据集上复现了 Kaplan 的缩放定律，识别出三个真正的成因——

  • 末层计算成本（last layer computational cost）
  • warmup 时长没有随模型规模缩放（固定 3000 步的 warmup 对小模型是偏长的，会污染小模型的数据点）
  • 优化器 / 学习率没有按尺度调参（scale-dependent optimizer tuning）

把这三点修正后，结果与 Chinchilla 完美吻合。而且他们还有个反直觉的发现：精细的学习率衰减并非 Chinchilla 定律成立的必要条件——这直接反驳了 Hoffmann 等人当初的一个假设。

Almeida 的观点是：那套「只怪参数怎么数」的主流解释其实不够准确，真正的病因是上面这套训练配置层面的 Bug。换句话说，问题不在「算账的方式」，而在「训练的方式」。

影响有多大：不只是烧掉的算力

这个 Bug 的代价，可以分几个层面看。

直接的算力浪费。 在 Chinchilla 出来之前的几年里，行业按照「做大模型」的思路，训练了一批参数量远超其数据量所能支撑的模型。GPT-3（175B / 300B tokens）、Gopher（280B / 300B tokens）都是典型。这些模型不仅训练时烧掉了本可省下的算力，推理时还要一直背着过大的参数量——每一次调用都在为当初的错误配比买单。媒体口中「数百万计算小时的浪费」，主要指的就是这部分。

方向的误导。 更隐蔽的代价是认知层面的。「模型越大越好」的信念，在那几年主导了融资叙事、硬件采购和产品路线。整个行业围绕「更大」而非「更均衡」去组织资源，这种惯性的纠偏成本，远比重训几个模型要高。

一个耐人寻味的收尾。 Almeida 提到，这个 Bug 最终被发现了，但据他所知从未被明确承认过——如今每个大厂其实都心知肚明。他甚至半开玩笑地建议：谁能给那篇原始论文加个勘误说明就好了。对非大厂的研究者，他的建议很直接：别在这个问题上浪费时间了，Chinchilla 的缩放定律才是对的那个。

那么，我们今天的训练方式就对了吗？

吸取了 Chinchilla 的教训，是不是就万事大吉、参数和数据 20:1 一配就完事了？没那么简单。这里恰恰是理解「当前训练方式对不对」的关键——Chinchilla 最优，不等于部署最优。

陷阱一：Chinchilla 只优化了「训练算力」，忽略了推理成本

Chinchilla 定律回答的问题是：给定训练算力预算，怎么配参数和数据，能让训练损失最低。 注意，它优化的只有训练这一次的算力。

但一个模型训练一次、推理无数次。如果你打算把模型部署出去服务海量请求，那么推理成本才是大头。这时候，理性的做法反而是故意偏离 Chinchilla 最优——把模型做得比「训练最优」更小，然后用远超 20 tokens/参数的数据去「过度训练」它。

LLaMA 系列就是这么干的：Llama 3 在 15T tokens 上训练一个相对小的模型，token/参数比远远超过 20。代价是训练阶段「不划算」，但换来的是推理时又快又便宜。对要长期服务用户的产品来说，这笔账完全算得过来。

所以结论是：「参数和数据是否匹配」没有唯一答案，取决于你优化的目标函数。

  • 只在乎训练算力（做研究、追 SOTA 损失）→ 向 Chinchilla 最优（~20 tokens/参数）靠拢。
  • 在乎全生命周期成本（要大规模部署）→ 小模型 + 超量数据，主动越过 Chinchilla 最优。

想深入了解推理侧的成本结构和框架选型，可以看：大模型推理框架选型对比 与 开源大模型选型指南。

陷阱二：数据墙——高质量的唯一 token 正在见底

Chinchilla 有个隐含假设：数据近乎无限，每个 token 都是唯一的、不重复的。 现实是，随着模型规模膨胀，我们正在用完互联网上高质量、不重复的 token。这就是所谓的「数据墙」。

一旦进入数据受限的区域，训练动力学会变得复杂：

  • 数据重复的双下降现象（Hernandez et al., 2022）：重复数据会让测试损失先变差、再变好，重复比例越高越明显。中段的平台/上升，很可能来自模型对重复数据的死记硬背。
  • 数据受限下的最优配比（Muennighoff et al., 2023）：当数据有限、不得不重复训练时，应该把总 token 拆成「唯一 token」和「重复次数」，用「有效数据量」去修正 Chinchilla 拟合。
  • 数据质量的缩放：同样是 D 个 token，一份精心清洗的高质量数据和一份互联网垃圾，带来的算力效率天差地别。D 背后的数据管线（去重、质量过滤、去样板、安全过滤、去污染、按语言/质量重新加权）本身就是训练的一大半功夫。

换句话说，「数据量」这个变量早就不是「有多少 token」这么简单了，质量和唯一性同样进入了方程。 只盯着参数量和 token 数的匹配，而不管数据质量，是新的刻舟求剑。

陷阱三：训练损失下降 ≠ 下游任务变好

缩放定律建模的是训练/测试损失。但我们真正关心的是下游任务表现。这两者的关系并不像想象中那么牢靠——有研究做了元分析，发现下游任务对缩放定律的「线性拟合」只有约 39% 的情况成立，而且看似无害的实验设置改动，就可能彻底改变缩放趋势。

这意味着：「损失按幂律下降」是可靠的，但「损失下降必然带来能力提升」需要单独验证。 用 pretraining loss 去外推「模型会不会更聪明」，本身就有风险。

陷阱四：这可能是「英语的」缩放定律

还有一个少被提及的维度。有研究者指出，Chinchilla 那个 ~20 tokens/参数的最优比，很可能是英语这门语言的最优。英语在形态学上相对贫乏，很多语法关系要靠上下文分布去推断，因此格外「吃数据」；而形态更丰富的语言（如法语），可能在少得多的数据上就达到同等语法能力。

如果这个观察成立，那么「多少数据算算力最优」就不只是算力问题，还是「你训练的是哪种语言」的问题。对中文等非英语场景的从业者来说，这是一个值得警惕、也值得自己动手验证的开放问题——而且它恰恰是非大厂研究者花小钱就能切入的方向。

给从业者的实操建议

把上面的讨论收敛成几条可执行的原则：

  • 别再用 Kaplan 的配比。 「把模型做大、别练到收敛」是被证伪的建议。默认从 Chinchilla（~20 tokens/参数）起步。
  • 先想清楚你在优化什么。 要部署、要服务海量请求，就主动越过 Chinchilla 最优，做「小模型 + 超量数据」，把成本压在推理侧。研究导向追损失，才回到训练算力最优。
  • 警惕学习率调度制造的「假饱和」。 Kaplan 的教训就是学习率衰减到零掩盖了真实趋势。评估「加数据还有没有用」时，务必把学习率调度作为一等变量来控制，而不是想当然。
  • 把数据质量当成一个独立维度。 token 数不等于有效数据量。去重、质量过滤、去污染、合理配比，往往比单纯堆 token 更能提升算力效率。
  • 别用 pretraining loss 直接推断下游能力。 下游表现要用下游评测单独验证，缩放曲线漂亮不代表任务表现一定跟得上。
  • 做多语言/中文场景，别照搬英语的经验比例。 20:1 未必是你的最优，值得自己小规模验证。

小结

Kaplan 缩放定律的 Bug，本质上是三个「合理」的训练配置叠加出的系统性偏差：固定 token 预算让大模型饥饿、衰减到零的学习率制造假性饱和、「与调度无关」的背书让 Bug 难以被质疑。它的直接后果，是行业花了几年时间训练又大又欠训练的模型，浪费了海量算力，也误导了整个「越大越好」的叙事。

Chinchilla 纠正了这个错误：参数和数据应当同步增长，约 20 tokens/参数。但这远不是终点。回到最初的问题——当前的训练方式对不对？参数和数据是否匹配？ 答案是：Chinchilla 给出了「训练算力最优」的正确基线，但真正的「正确」取决于你的目标。要部署就得为推理成本让路（小模型、超量数据）；要在数据墙前生存就得把质量和唯一性纳入方程；要相信能力提升就得用下游评测而非损失曲线去验证。

一个 Bug 教会我们的，或许不是「Chinchilla 才对」这么简单，而是——任何一条看起来铁律般的缩放曲线，背后都藏着一堆没被写进结论的前提假设。 对这些假设保持怀疑，才是「honestly」的正确姿势。
