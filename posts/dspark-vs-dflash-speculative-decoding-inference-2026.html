DSpark 提速 85%、DFlash 加速 6x——推理加速两大技术路线怎么选？

AI 基础设施 2026-07-02 · 14 分钟

2026 年 6 月最后一周，大模型推理加速领域接连放出两枚重磅炸弹：DeepSeek 联合北京大学开源了 DSpark 推理加速框架，实测让 V4-Flash 线上生成速度提升 85%；几乎同一时间，NVIDIA 官方博客宣布 DFlash 在 Blackwell GPU 上实现 15x 吞吐提升。两套方案都瞄准"投机解码"（Speculative Decoding）这一技术赛道，却走出了截然不同的路线。

对于正在构建大模型推理服务的团队来说，一个现实的问题摆在面前：选 DSpark 还是 DFlash？两者能不能共存？

本文将从技术原理、性能数据、适用场景三个维度，拆解这两大框架的核心差异，并给出选型建议。

一、投机解码：为什么这是 2026 年的必争之地

在进入正题之前，先快速对齐一下背景。

大模型推理的核心瓶颈不在计算，而在访存。自回归生成（Autoregressive Generation）每一步只产出一个 token，但每产出一个 token，GPU 都要从显存中加载数百亿参数的模型权重和不断增长的 KV Cache。计算单元大部分时间在"等数据"，利用率极低。

投机解码的核心思想是引入一个轻量级"草稿模型"（Draft Model），让它快速预测后续若干 token，再由目标大模型一次性批量验证。命中的 token 直接采纳，未命中的丢弃并从出错点继续。由于验证是并行的，一次验证通过 N 个 token 的成本远低于逐个生成 N 次。

2025 年以来，投机解码已从学术论文走向生产部署。EAGLE-3、Medusa、PARD 等方案各有千秋，但 2026 年上半年，DSpark 和 DFlash 以碾压级的性能数据脱颖而出，成为新一代"双雄"。

二、DSpark：置信度调度 + 半自回归生成

2.1 核心思想

DSpark 的全称是 Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation。论文由 DeepSeek 创始人梁文锋联合北京大学共同发表，2026 年 6 月 27 日公开。

它解决的核心问题是：传统投机解码中，草稿模型"盲猜"一段话，目标模型必须对整段话执行完整验证。如果草稿后半段全错，验证这些错误 token 消耗的计算就是纯浪费。

DSpark 的两大创新：

  • 半自回归生成（Semi-Autoregressive Generation）：草稿模型不再完全独立地逐 token 生成，而是在每一步利用前一步的隐状态引导下一步的生成，提高序列后段的命中率。

  • 置信度调度（Confidence-Scheduled Verification）：草稿模型在输出时额外产生一个置信度标量。系统根据置信度动态决定"验证到哪里就停"——高置信段优先验证，低置信段直接丢弃，不再浪费 GPU 算力。

2.2 生产环境数据

DSpark 已在 DeepSeek-V4 的线上服务中正式部署，面对真实用户流量：

  • 单用户生成速度：提升 60%-85%（Flash 版本），57%-78%（Pro 版本）
  • 高并发聚合吞吐：提升 51%-400%（在线场景）、最高 661%（离线场景）
  • 对比 EAGLE-3：平均接受长度（Acceptance Length）提升 26.7%-30.9%
  • 对比 DFlash：平均接受长度提升 16.3%-18.4%（Qwen3 系列离线测试）

2.3 配套开源：DeepSpec 框架

DSpark 随 DeepSpec 框架一并开源（MIT 协议）。DeepSpec 不只包含 DSpark，还集成了 DFlash 和 Eagle3 的实现，提供标准化的草稿模型训练与评估管线。开发者可以在统一框架下对比不同投机解码方案的效果。

目前 Hugging Face 上已有 deepseek-ai/DeepSeek-V4-Pro-DSpark 等预训练草稿模型可供直接使用。

三、DFlash：块扩散一步起草

3.1 核心思想

DFlash 的全称是 Block Diffusion for Flash Speculative Decoding。论文由 z-lab 团队于 2026 年 2 月发表，NVIDIA 随后在 Blackwell 平台上进行深度工程优化并官方推广。

它解决的核心问题是：传统草稿模型（包括 EAGLE-3）仍然是自回归的——每预测一个 token 需要一次前向传播，草稿越长计算越贵，且误差沿序列累积。

DFlash 的核心创新：

  • 块扩散草稿模型（Block Diffusion Drafter）：用一个轻量级扩散模型，在单次前向传播中并行生成整块 K 个候选 token。草稿成本不再随 K 线性增长。

  • 目标模型特征条件化：草稿模型以目标大模型的中间层特征为条件输入，使得生成质量更高、接受率更高。

3.2 性能数据

  • 无损加速：在 Qwen3-8B 上实现 6x 加速
  • 对比 EAGLE-3：速度高出 2.5x
  • NVIDIA Blackwell 上（TensorRT-LLM 集成）：在 500-600 tok/s/user 的交互性目标下，吞吐量达到标准自回归解码的 15x，EAGLE-3 的 1.5x
  • Baseten 实测：在 B200 GPU 上对 Qwen3-8B 实现约 3x 延迟加速

3.3 生态与适配

DFlash 由 z-lab 团队维护，GitHub 开源（z-lab/dflash）。目前已提供以下模型的预训练草稿模型：

  • Qwen3-8B / Qwen3.5-35B-A3B
  • Gemma 4-31B-it / Gemma 4-26B-A4B-it
  • GPT-oss-20B
  • 与 vLLM、TensorRT-LLM 均有集成

NVIDIA 已将 DFlash 纳入 Blackwell 推理生态的官方推荐方案。

4.1 技术路线的本质差异

两者的根本分歧在于"如何起草"和"如何验证"：

  • DFlash 的革命在起草端：用扩散模型替代自回归起草，彻底打破"草稿越长越贵"的线性约束。单次前向就能出 8-16 个候选 token，起草成本几乎为常数。

  • DSpark 的革命在验证端：承认草稿不可能全对，但通过置信度评估"聪明地"跳过注定错误的部分。不验证 = 不浪费算力。

这意味着两者在理论上是互补的——可以用 DFlash 式的块扩散做高效起草，再用 DSpark 式的置信度调度做智能验证。事实上，DeepSpec 框架同时包含两者的实现，暗示了这一融合方向。

4.2 长上下文场景的挑战

值得注意的是，学术研究已发现投机解码在长生成场景下存在衰退问题。论文 "Test-Time Speculation" 指出，即便是 DFlash 和 EAGLE-3 等先进方法，随着生成长度增加，acceptance length 会逐渐下降至接近 1（即几乎无加速）。

DSpark 的置信度调度在一定程度上缓解了这一问题——当置信度下降时，系统主动缩短验证窗口，避免在低效区间浪费算力。但彻底解决长生成衰退，仍是整个领域的开放问题。

五、选型指南：什么场景选什么方案

5.1 选 DSpark 的场景

  • 你在使用 DeepSeek-V4 系列模型：DSpark 对 V4 的 MHC（Multi-Head Cache）架构有深度适配，开箱即用
  • 高并发、多样化流量：置信度调度在流量波动大的场景下表现稳健，能自适应负载
  • 需要端到端集成方案：DeepSpec 提供从训练到评估到部署的完整管线
  • 团队有充足存储资源：训练草稿模型需约 38TB 目标缓存（中型模型规模）

5.2 选 DFlash 的场景

  • 你在使用 Qwen3、Gemma 4 或其他通用模型：DFlash 的预训练草稿模型覆盖面广
  • 硬件是 NVIDIA Blackwell：DFlash + TensorRT-LLM 有 NVIDIA 官方工程优化加持
  • 单用户延迟敏感：块扩散一次性出整块 token，首批草稿速度极快
  • 快速验证可行性：z-lab 提供现成的草稿模型权重，pip install 即可测试

5.3 两者共存的方案

正如 DeepSpec 框架的设计所暗示的，最优解可能是混合使用：

  • 用 DFlash 的块扩散做快速起草
  • 用 DSpark 的置信度调度做智能验证截断
  • 根据请求类型动态路由（短文本用 DFlash 直出，长文本用 DSpark 的自适应调度）

这种"最佳组合"目前尚无公开的生产部署案例，但从 DeepSpec 的代码结构来看，这是 DeepSeek 正在探索的方向。

六、更大的图景：推理成本战的下一步

DSpark 和 DFlash 的同时爆发不是巧合。它揭示了 2026 年大模型竞争的核心逻辑转变：

从"谁的模型更聪明"到"谁的推理更便宜"。

当各家模型在基准测试上的差距越来越小时，决定商业竞争力的不再是多几个百分点的 benchmark 得分，而是：

  • 同样的 GPU 集群，能服务多少用户？
  • 同样的用户体验，成本能压到多低？
  • 同样的预算，能跑多复杂的 Agent 工作流？

投机解码正从"锦上添花的优化技巧"变成"生产部署的标配基础设施"。未来的推理服务栈，大概率会像今天的数据库引擎一样，将投机解码、KV Cache 压缩、量化推理等优化内化为底层能力，对上层应用透明。

对于开发者而言，现在就是上车的好时机。DSpark 和 DFlash 都以 MIT 或类似宽松协议开源，技术门槛已大幅降低。

推理加速的竞赛才刚刚进入深水区。
